\subsection{Datos ordenados (\emph{tidy data})}
\label{sec:m2-tidy}

Antes de transformar datos conviene saber a qué forma queremos llegar. El
estadístico Hadley Wickham, creador de buena parte de los paquetes de este
módulo, propuso una forma estándar llamada \termino{datos ordenados}
(\emph{tidy data}).

\begin{concepto}{Las tres reglas de los datos ordenados}
Una tabla está \emph{ordenada} cuando cumple tres reglas:
\begin{enumerate}
  \item \textbf{Cada variable es una columna.} Fecha, sucursal, producto y
        monto son cuatro variables: cuatro columnas.
  \item \textbf{Cada observación es una fila.} Una venta, un cliente o un
        mes de una sucursal ocupa una fila.
  \item \textbf{Cada valor está en su propia celda.} Nada de
        ``\texttt{CDMX-Centro}'' en una celda si ciudad y zona son cosas
        distintas.
\end{enumerate}
Cuando tus datos cumplen estas reglas, todas las funciones del
\emph{tidyverse} ``encajan'': filtras, agrupas, unes y graficas sin pelearte
con la forma de la tabla.
\end{concepto}

El ejemplo más común de datos \emph{desordenados} en una empresa es el reporte
de Excel ``bonito'', pensado para leerse, no para analizarse. En la
tabla~\ref{tab:m2-tidy} el reporte de la izquierda tiene los meses como
columnas: la variable \emph{mes} está escondida en los encabezados y la
variable \emph{ventas} está repartida en tres columnas. La versión ordenada
(derecha) tiene una columna por variable.

¿Por qué es mejor la versión larga? Porque preguntas como ``¿cuánto se vendió
en total en febrero?'' o ``¿qué mes fue el mejor de cada sucursal?'' se
resuelven con un filtro o un agrupamiento, sin importar si mañana el reporte
trae 3 meses o 36. En la sección~\ref{sec:m2-tidyr} aprenderás a pasar de una
forma a la otra con una sola función. Otros síntomas de datos desordenados que
encontrarás en la práctica son:

\begin{itemize}
  \item Dos datos en una celda: \texttt{"Guadalajara, Jal."} o
        \texttt{"2023-Q1"}.
  \item Celdas combinadas de Excel: la región aparece solo en la primera fila
        del bloque y las demás quedan vacías.
  \item Totales y subtotales mezclados con los datos (la fila ``Total
        general'' al final).
  \item Varias tablas en una misma hoja, o encabezados en dos renglones.
\end{itemize}

Si todavía no lo tienes, instala el \emph{tidyverse} y el paquete

por computadora:

\begin{rnoejecutar}
# Se ejecuta UNA sola vez (tarda unos minutos)
install.packages(c("tidyverse", "writexl"))
\end{rnoejecutar}

Y al inicio de cada script cargas los paquetes (esto sí, cada vez):

\begin{rcode}
# Carga dplyr, tidyr, readr, stringr, lubridate, ggplot2, etc.
library(tidyverse)
# writexl no es parte del tidyverse: se carga aparte
library(writexl)
\end{rcode}

Al cargar el \emph{tidyverse} verás un mensaje de bienvenida con dos partes.
La primera, \emph{Attaching core tidyverse packages}, lista los nueve paquetes
que se cargaron y sus versiones. La segunda, \emph{Conflicts}, avisa que
algunas funciones ``tapan'' (\emph{mask}) a otras con el mismo nombre; por
ejemplo, \codigo{dplyr::filter() masks stats::filter()} significa que, a
partir de ahora, cuando escribas \codigo{filter()} R usará la versión de
\paquete{dplyr} y no la del paquete base \paquete{stats}. No es un error:
es un aviso, y es justo lo que queremos. (En la sección~\ref{sec:m2-errores}
verás qué pasa cuando olvidas cargar el paquete.)

\begin{consejo}
La notación \codigo{paquete::funcion()} llama a una función de un paquete
específico sin ambigüedad, aunque haya otra con el mismo nombre. Por ejemplo,
\codigo{dplyr::filter()} siempre es el filtro de \paquete{dplyr}. La verás
en foros y en código profesional; también sirve para usar una función de un
paquete instalado sin cargarlo con \codigo{library()}.
\end{consejo}

\subsection{Tu primera lectura con \texorpdfstring{\codigo{read\_csv()}}{read\_csv()}}

Un \termino{CSV} (\emph{comma-separated values}) es un archivo de texto donde
cada renglón es una fila y las columnas se separan con comas. Es el formato
más común para intercambiar datos entre sistemas: casi cualquier ERP, CRM o
base de datos puede exportar a CSV. La función \codigo{read\_csv()} de
\paquete{readr} lo lee y devuelve un \emph{tibble}.

Recuerda que todas las rutas del libro son relativas a la carpeta del curso
(la que contiene \archivo{datasets/}). Si en RStudio abriste el proyecto del
curso, ya estás ahí; si no, revisa el Módulo~\ref{cap:fundamentos}.

\begin{rcode}
# Leer el archivo de ventas y guardarlo en el objeto "ventas"
ventas <- read_csv("datasets/ventas_retail.csv")
\end{rcode}
En la consola aparece este mensaje:
\begin{rsalida}
@@SALIDA@@
\end{rsalida}

Este mensaje, la \termino{especificación de columnas}, no es un error: es
\paquete{readr} contándote qué hizo. Léelo de arriba abajo:

\begin{itemize}
  \item \texttt{Rows: 365 Columns: 14}: se leyeron 365 filas (una venta por
        día de 2023) y 14 columnas. Compara siempre estos números con lo que
        esperabas; es tu primera prueba de calidad.
  \item \texttt{Delimiter: ","}: el separador que detectó.
  \item \texttt{chr (3)}: tres columnas de texto (\emph{character}).
  \item \texttt{dbl (10)}: diez columnas numéricas (\emph{double}, números
        con decimales). Los identificadores como \codigo{producto\_id}
        también se leyeron como números.
  \item \texttt{date (1)}: una columna de fecha. \paquete{readr} reconoció
        el formato \texttt{2023-01-01} y lo convirtió automáticamente.
\end{itemize}

\paquete{readr} \emph{adivina} el tipo de cada columna mirando las primeras
1000 filas. Casi siempre acierta, pero no siempre (lo verás en un momento).
Cuando ya conoces el archivo, puedes silenciar el mensaje con
\codigo{show\_col\_types = FALSE}, que es lo que haremos en el resto del
libro.

\subsection{Controlar los tipos con \texorpdfstring{\codigo{col\_types}}{col\_types}}

A veces la adivinanza de \paquete{readr} no es lo que necesitas. Un caso
típico son los identificadores: \codigo{cliente\_id} es una etiqueta, no una
cantidad (sumar identificadores no tiene sentido). Con el argumento
\codigo{col\_types} le dices a \paquete{readr} exactamente cómo leer cada
columna; las que no menciones se siguen adivinando.

\begin{rcode}
# Leer los identificadores como texto y la cantidad como entero
ventas_tipos <- read_csv(
  "datasets/ventas_retail.csv",
  col_types = cols(
    producto_id = col_character(),   # texto
    cliente_id  = col_character(),   # texto
    cantidad    = col_integer(),     # número entero
    .default    = col_guess()        # el resto: que readr adivine
  )
)
# Revisamos solo las columnas que nos interesan
glimpse(select(ventas_tipos, producto_id, cliente_id, cantidad))
\end{rcode}
\begin{rsalida}
Rows: 365
Columns: 3
$ producto_id <chr> "31", "15", "14", "3", "42", "50", "43", "37", "~
$ cliente_id  <chr> "94", "169", "136", "167", "81", "191", "82", "1~
$ cantidad    <int> 10, 8, 3, 2, 10, 8, 10, 7, 7, 6, 1, 4, 1, 5, 10,~
\end{rsalida}

{\sloppy Ahora \codigo{producto\_id} es \texttt{<chr>} y \codigo{cantidad} es
\texttt{<int>} (entero). Las funciones más usadas en \codigo{cols()} son
\codigo{col\_character()}, \codigo{col\_double()}, \codigo{col\_integer()},
\codigo{col\_logical()}, \codigo{col\_date(format = "\%d/\%m/\%Y")} y
\codigo{col\_skip()} (para no leer una columna). Si solo necesitas algunas
columnas de un archivo grande, \codigo{col\_select} lee únicamente esas:
\codigo{read\_csv(ruta, col\_select = c(fecha, total))}.\par}

\begin{advertencia}
Para unir tablas (sección~\ref{sec:m2-joins}), la llave debe tener el
\emph{mismo tipo} en ambas. Si lees \codigo{producto\_id} como texto en
ventas y como número en productos, el \emph{join} fallará con un error
\texttt{Can't join ... due to incompatible types}. En este módulo dejaremos
los identificadores como números en todas las tablas para evitarlo.
\end{advertencia}

\subsection{Cuando algo sale mal: \texorpdfstring{\codigo{problems()}}{problems()}}

Imagina que la sucursal Norte te manda su inventario y alguien escribió
``N/D'' y ``sin dato'' en lugar de un número. Para simular ese archivo, lo
creamos nosotros mismos con \codigo{write\_lines()} (cada elemento es un
renglón del archivo) en una carpeta \archivo{datos/}:

\begin{rcode}
# Crear la carpeta datos/ (si ya existe, no pasa nada)

write_lines(c("sucursal,producto,existencias",

              "Sur,P02,85",
              "Este,P02,sin dato"),
            "datos/inventario.csv")
# Leerlo exigiendo que existencias sea numérica
inventario <- read_csv("datos/inventario.csv",
                       col_types = cols(existencias = col_double()))
\end{rcode}
\begin{rsalida}

details, e.g.:
  dat <- vroom(...)
  problems(dat)

\paquete{readr} no se detiene: lee lo que puede, pone \codigo{NA} (valor

muestra la ruta completa del archivo; aquí la omitimos para ahorrar espacio):

\begin{rcode}
problems(inventario) %>%
  select(row, col, expected, actual)
\end{rcode}

columna 3, esperaban un número y encontraron \texttt{N/D} y
\texttt{sin dato}. Como sabemos que esos textos significan ``no hay dato'',
la solución limpia es decírselo a \paquete{readr} con el argumento
\codigo{na}:

  sucursal producto existencias

1 Centro   P01              120
2 Norte    P01               NA
3 Sur      P02               85
4 Este     P02               NA
\end{rsalida}

Ya no hay advertencia y \codigo{existencias} es numérica

\section{El pipe: encadenar pasos como una receta}
\label{sec:m2-pipe}

Supón que quieres ver las ventas de la tienda 1 en diciembre, solo con la
fecha, el producto, la cantidad y el total, de la más grande a la más
chica. Son tres pasos: filtrar, seleccionar columnas y ordenar. Hay tres
maneras de escribirlo.

\textbf{Opción 1: funciones anidadas.} Cada función envuelve a la anterior.
Funciona, pero se lee de adentro hacia afuera y los argumentos quedan lejos
de su función:

\begin{rcode}
arrange(
  select(
    filter(ventas, tienda_id == 1, mes == "2023-12"),
    fecha, producto_id, cantidad, total
  ),
  desc(total)
)
\end{rcode}

\textbf{Opción 2: objetos intermedios.} Se lee mejor, pero llenas tu
ambiente de objetos (\codigo{paso1}, \codigo{paso2}\ldots) que no vuelves a
usar, y es fácil equivocarte de nombre:

\begin{rcode}
paso1 <- filter(ventas, tienda_id == 1, mes == "2023-12")
paso2 <- select(paso1, fecha, producto_id, cantidad, total)
paso3 <- arrange(paso2, desc(total))
\end{rcode}

\textbf{Opción 3: el pipe.} El operador \codigo{\%>\%}, llamado
\termino{pipe} (tubería), toma lo que está a su izquierda y lo pasa como
\emph{primer argumento} a la función de su derecha. Así,
\codigo{x \%>\% f(y)} es lo mismo que \codigo{f(x, y)}:

\begin{rcode}
ventas %>%                                   # toma las ventas,
  filter(tienda_id == 1, mes == "2023-12") %>% # y luego filtra,
  select(fecha, producto_id, cantidad, total) %>% # y luego elige,
  arrange(desc(total))                       # y luego ordena
\end{rcode}
\begin{rsalida}
# A tibble: 5 x 4
  fecha      producto_id cantidad  total
  <date>           <dbl>    <dbl>  <dbl>
1 2023-12-18          18        9 2646. 
2 2023-12-26          26        5 1847. 
3 2023-12-12          35        3  441. 
4 2023-12-24          42        1  349. 
5 2023-12-25          32        1   54.0
\end{rsalida}

Las tres opciones dan exactamente el mismo resultado, pero la tercera se lee
de arriba abajo como una receta. Lee cada \codigo{\%>\%} como
\textbf{``y luego''}: \emph{``toma las ventas, y luego filtra la tienda 1 en
diciembre, y luego elige cuatro columnas, y luego ordena por total
descendente''}. La tienda 1 tuvo 5 ventas en diciembre y la mayor fue de
\$2,646 el 18 de diciembre.

\begin{consejo}
El atajo de teclado para escribir el pipe en RStudio es
\tecla{Ctrl} + \tecla{Shift} + \tecla{M} (en Mac, \tecla{Cmd} +
\tecla{Shift} + \tecla{M}). Úsalo desde hoy: lo vas a teclear cientos de
veces al día. Escribe un paso por línea y deja el \codigo{\%>\%} \emph{al
final} de la línea, nunca al principio de la siguiente.
\end{consejo}

\subsection{El pipe nativo \texorpdfstring{\codigo{|>}}{|>}}

Desde la versión 4.1, R trae su propio pipe, el \termino{pipe nativo}
\codigo{|>}, que no necesita cargar ningún paquete. Para el trabajo diario
ambos hacen lo mismo:

\begin{rcode}
# Mismo resultado que con %>%: contar las ventas de diciembre
ventas |>
  filter(mes == "2023-12") |>
  nrow()
\end{rcode}
\begin{rsalida}
[1] 31
\end{rsalida}

Las diferencias que te pueden afectar son pocas:

\begin{itemize}
  \item \codigo{|>} siempre exige paréntesis: \codigo{ventas |> nrow()}
        funciona pero \codigo{ventas |> nrow} da error, mientras que
        \codigo{ventas \%>\% nrow} sí funciona.
  \item Para mandar el dato a un argumento que no es el primero,
        \codigo{\%>\%} usa un punto (\codigo{data = .}) y \codigo{|>} usa un
        guion bajo con nombre (\codigo{data = \_}, desde R 4.2).
  \item \codigo{\%>\%} viene del paquete \paquete{magrittr} y se carga con
        el \emph{tidyverse}; \codigo{|>} está siempre disponible.
\end{itemize}

En este libro usamos \codigo{\%>\%} porque es el que encontrarás en la
mayoría de los ejemplos en internet, pero puedes usar el que prefieras. Si
quieres que el atajo \tecla{Ctrl} + \tecla{Shift} + \tecla{M} escriba
\codigo{|>}, activa la casilla \emph{Use native pipe operator} en
\menu{Tools > Global Options > Code}.

\begin{hazlotu}
Reescribe con pipe la siguiente instrucción anidada y léela en voz alta
usando ``y luego'':
\begin{rnoejecutar}

\end{rnoejecutar}
\end{hazlotu}

\section{Los verbos de \texorpdfstring{\paquete{dplyr}}{dplyr}}
\label{sec:m2-verbos}

\paquete{dplyr} está construido alrededor de unos cuantos \termino{verbos}:
funciones cuyo nombre dice lo que hacen con la tabla. Todos siguen las mismas
reglas, y una vez que las entiendes, aprender un verbo nuevo es trivial:

\begin{enumerate}
  \item El primer argumento siempre es un \emph{data frame} (por eso encajan
        tan bien con el pipe).
  \item Los demás argumentos usan los nombres de las columnas \emph{sin
        comillas} y sin \codigo{\$}: escribes \codigo{total}, no
        \codigo{ventas\$total}.
  \item El resultado siempre es un \emph{data frame} nuevo. La tabla original
        \emph{no se modifica}; si quieres conservar el resultado, guárdalo con
        \codigo{<-}.
\end{enumerate}

\subsection{\texorpdfstring{\codigo{filter()}}{filter()}: quedarte con las filas que importan}
\label{sec:m2-filter}

\codigo{filter()} recibe una o más condiciones lógicas y conserva solo las
filas donde la condición es \codigo{TRUE}. Las condiciones se construyen con
los operadores de la tabla~\ref{tab:m2-operadores}.

\begin{table}[H]
\centering
\caption{Operadores para construir condiciones en \codigo{filter()}.}
\label{tab:m2-operadores}
\small
\begin{tabularx}{\textwidth}{@{}lXl@{}}
\toprule
Operador & Significado & Ejemplo \\
\midrule
\codigo{==}  & Igual a (¡dos signos!) & \codigo{tienda\_id == 3} \\
\codigo{!=}  & Distinto de & \codigo{trimestre != "Q4"} \\
\codigo{>}, \codigo{>=} & Mayor, mayor o igual & \codigo{total >= 1000} \\
\codigo{<}, \codigo{<=} & Menor, menor o igual & \codigo{cantidad < 3} \\
\codigo{\&} o coma & Y: se deben cumplir ambas & \codigo{tienda\_id == 1, cantidad > 5} \\
\codigo{|}   & O: basta con que se cumpla una & \codigo{descuento\_pct == 20 | cantidad == 10} \\
\codigo{!}   & No (niega la condición) & \codigo{!activo} \\
\codigo{\%in\%} & Pertenece a una lista de valores & \codigo{tienda\_id \%in\% c(1, 4)} \\
\codigo{between()} & Dentro de un rango (incluye extremos) & \codigo{between(total, 500, 900)} \\
\codigo{is.na()} & Es un valor faltante & \codigo{is.na(email)} \\
\bottomrule
\end{tabularx}
\end{table}

\begin{ejemplo}{Una u otra condición (O) y listas de valores}
Mercadotecnia quiere las ventas ``extremas'': las que tuvieron el descuento
máximo (20\%) \emph{o} se llevaron 10 unidades. Y, aparte, las ventas de
las cuatro tiendas de la CDMX (tiendas 1, 4, 6 y 9).
\end{ejemplo}

\begin{rcode}
# O: basta con que se cumpla una de las dos condiciones
ventas %>%
  filter(descuento_pct == 20 | cantidad == 10) %>%
  nrow()

# %in%: la tienda está en la lista (más corto que cuatro "|")
ventas_cdmx <- ventas %>%
  filter(tienda_id %in% c(1, 4, 6, 9))
nrow(ventas_cdmx)
\end{rcode}
\begin{rsalida}
[1] 54
[1] 135
\end{rsalida}

legible y evitas errores como escribir
\codigo{tienda\_id == 1 | 4}, que \emph{no} significa lo que parece.

\begin{advertencia}

Luis y Jorge no aparecieron en el primer filtro \emph{ni aparecerían} con
\codigo{meta <= 45000}. Si necesitas conservarlos, sé explícito:
\codigo{filter(meta > 45000 | is.na(meta))}.

\subsection{\texorpdfstring{\codigo{select()}}{select()}: elegir, quitar y renombrar columnas}
\label{sec:m2-select}

Las tablas reales tienen decenas de columnas y casi nunca las necesitas

\begin{ejemplo}{Una lista de precios para el equipo de ventas}
El equipo de piso solo necesita el nombre, la categoría y el precio de cada

lista_precios <- productos %>%
  select(nombre_producto, categoria, precio_catalogo)   # por nombre

  nombre_producto categoria  precio_catalogo
  <chr>           <chr>                <dbl>
1 Producto 01     Juguetes              300.
2 Producto 02     Belleza               313.
3 Producto 03     Automotriz            400.
4 Producto 04     Juguetes              744.
\end{rsalida}

\subsection{\texorpdfstring{\codigo{mutate()}}{mutate()}: crear columnas calculadas}
\label{sec:m2-mutate}

\codigo{mutate()} agrega columnas nuevas (o reemplaza existentes) calculadas
a partir de las demás. Es el equivalente a escribir una fórmula en una
columna de Excel y arrastrarla hacia abajo, solo que se aplica a todas las
filas de una vez y queda documentada en el código.

\begin{ejemplo}{IVA y total con impuestos}
Los montos de \codigo{ventas} no incluyen IVA. Contabilidad necesita, para
cada venta, el IVA (16\%) y el total facturado.

ventas %>%
  mutate(
    iva            = total * 0.16,        # 16% sobre el total
    total_con_iva  = total + iva          # usa la columna recién creada
  ) %>%
  select(fecha, subtotal, descuento_monto, total, iva, total_con_iva) %>%
  head(4)

\subsubsection{Condiciones: \texorpdfstring{\codigo{if\_else()}}{if\_else()} y \texorpdfstring{\codigo{case\_when()}}{case\_when()}}

\codigo{if\_else(condición, valor\_si\_verdadero, valor\_si\_falso)} crea
una columna con dos posibles valores, como la función \codigo{SI()} de
Excel:

\begin{rcode}
ventas %>%
  mutate(tipo_dia = if_else(dia_semana %in% c("sábado", "domingo"),
                            "Fin de semana", "Entre semana")) %>%
  count(tipo_dia)
\end{rcode}
\begin{rsalida}
# A tibble: 2 x 2
  tipo_dia          n
  <chr>         <int>
1 Entre semana    260
2 Fin de semana   105
\end{rsalida}

Cuando hay más de dos opciones, anidar \codigo{if\_else()} se vuelve
ilegible. Para eso existe \codigo{case\_when()}: una lista de reglas
\codigo{condición \textasciitilde{} valor} que se evalúan \emph{en orden}; a cada
fila se le asigna el valor de la \emph{primera} regla que cumple.

\begin{ejemplo}{Segmentar ventas por tamaño de ticket}
Mercadotecnia quiere clasificar cada venta en cuatro segmentos: Chico
(menos de \$500), Mediano (\$500 a \$1,499), Grande (\$1,500 a \$2,999) y
Premium (\$3,000 o más). ¿Cuántas ventas y cuánto dinero hay en cada uno?
\end{ejemplo}

\begin{rcode}
ventas_segmentadas <- ventas %>%
  mutate(segmento_ticket = case_when(
    total < 500   ~ "1. Chico",       # se evalúa primero
    total < 1500  ~ "2. Mediano",     # solo si no fue Chico
    total < 3000  ~ "3. Grande",
    .default      = "4. Premium"      # todo lo demás
  ))

ventas_segmentadas %>%
  group_by(segmento_ticket) %>%
  summarise(ventas = n(), ingresos = sum(total))
\end{rcode}
\begin{rsalida}
# A tibble: 4 x 3
  segmento_ticket ventas ingresos
  <chr>            <int>    <dbl>
1 1. Chico            98   25588.
2 2. Mediano         129  125261.
3 3. Grande          101  227370.
4 4. Premium          37  135697.
\end{rsalida}

Una lectura de negocio: los tickets Premium son solo 37 ventas (una de
cada diez), pero generan \$135,697, más de cinco veces lo que dejan los 98
tickets Chicos juntos (\$25,588). El segmento que más dinero aporta es el
Grande (\$227,370). La estrategia comercial debe cuidar a los tickets
altos. (Adelantamos
\codigo{group\_by()} y \codigo{summarise()}, que veremos en detalle muy
pronto.)

\begin{consejo}
Pon un número al inicio de cada etiqueta (``1. Chico'', ``2. Mediano''\ldots)
y los grupos aparecerán en orden lógico y no alfabético. El argumento
\codigo{.default} (dplyr 1.1 o posterior) asigna un valor a todo lo que no
cumplió ninguna regla; en código antiguo verás \codigo{TRUE \textasciitilde{} "Premium"},
que hace lo mismo.
\end{consejo}

\subsubsection{Varias columnas a la vez: \texorpdfstring{\codigo{across()}}{across()}}

Si quieres aplicar la misma operación a varias columnas, no repitas el
código: usa \codigo{across(columnas, función)}. Las columnas se eligen con
la misma sintaxis de \codigo{select()}.

\begin{rcode}
# Redondear a 0 decimales las tres columnas de dinero
ventas %>%
  mutate(across(c(subtotal, descuento_monto, total), round)) %>%
  select(fecha, subtotal, descuento_monto, total) %>%
  head(3)

# Con una función "al vuelo": ~ .x indica "cada columna"
productos %>%
  mutate(across(c(precio_catalogo, costo), ~ .x * 1.16,
                .names = "{.col}_con_iva")) %>%
  select(nombre_producto, ends_with("_con_iva")) %>%
  head(3)
\end{rcode}

\subsubsection{Conservar solo lo calculado: \texorpdfstring{\codigo{.keep}}{.keep} y \texorpdfstring{\codigo{transmute()}}{transmute()}}

Por defecto, \codigo{mutate()} conserva todas las columnas. Con el argumento
\codigo{.keep} decides qué más se queda: \codigo{"used"} (solo las columnas
usadas en el cálculo) o \codigo{"none"} (solo las nuevas). La antigua función
\codigo{transmute()} equivale a \codigo{.keep = "none"}.

\begin{rcode}
# Solo las columnas que participaron en el cálculo, más la nueva
ventas %>%
  mutate(precio_neto = total / cantidad, .keep = "used") %>%
  head(3)

# Solo las nuevas (equivalente a transmute())
ventas %>%
  mutate(anio = str_sub(mes, 1, 4), ticket = round(total),
         .keep = "none") %>%
  head(3)
\end{rcode}

  anio  ticket
  <chr>  <dbl>

\begin{advertencia}
\codigo{mutate()} no modifica \codigo{ventas}: devuelve una copia con la
columna nueva. Si ejecutas \codigo{ventas \%>\% mutate(iva = total * 0.16)}
y luego buscas \codigo{ventas\$iva}, no existirá. Para conservarla escribe

en un objeto con otro nombre y deja intacta la tabla original.

# La venta más grande de cada trimestre

productos %>%

\subsection{\texorpdfstring{\codigo{summarise()}}{summarise()} y \texorpdfstring{\codigo{group\_by()}}{group\_by()}: de miles de filas a un KPI}
\label{sec:m2-summarise}

\codigo{summarise()} (o \codigo{summarize()}, ambas funcionan) reduce muchas
filas a una sola fila de resultados. Dentro usas \termino{funciones de
resumen}: reciben un vector de muchos valores y devuelven uno solo.

\begin{table}[H]
\centering
\caption{Funciones de resumen más usadas en BI.}
\label{tab:m2-resumen-fun}
\small
\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
Función & Qué calcula \\
\midrule
\codigo{n()} & Número de filas (transacciones, registros) \\
\codigo{n\_distinct(x)} & Número de valores distintos (clientes únicos, productos vendidos) \\
\codigo{sum(x)} & Suma (ingresos, unidades) \\
\codigo{mean(x)}, \codigo{median(x)} & Promedio y mediana (ticket promedio, ticket típico) \\

\begin{ejemplo}{El tablero de KPIs del año}
La dirección quiere los indicadores clave de 2023 en una sola tabla:
ingresos, número de ventas, unidades, ticket promedio y mediano, venta mínima
y máxima, y clientes únicos.
\end{ejemplo}

\begin{rcode}
kpis_2023 <- ventas %>%

\subsubsection{Agrupar por varias columnas y el argumento \texorpdfstring{\codigo{.groups}}{.groups}}

Puedes agrupar por más de una columna. Observa el mensaje que aparece:

\begin{rcode}
ventas_trim_tienda <- ventas %>%
  group_by(trimestre, tienda_id) %>%
  summarise(ingresos = sum(total))
\end{rcode}
\begin{rsalida}

using the `.groups` argument.

No es un error. \paquete{dplyr} te avisa que el resultado \emph{sigue
agrupado} por \codigo{trimestre}: cada \codigo{summarise()} ``pela'' solo el
último nivel de agrupación. Esto importa porque cualquier cálculo posterior
se hará por trimestre. Para no llevarte sorpresas, di explícitamente qué
quieres con \codigo{.groups}:

\begin{rcode}
ventas_trim_tienda <- ventas %>%
  group_by(trimestre, tienda_id) %>%
  summarise(ingresos = sum(total), .groups = "drop")  # sin grupos

\end{rcode}

c(trimestre, tienda\_id))} equivale al código anterior. Verás ambas formas
en código real; en este libro usamos \codigo{group\_by()} porque es la más
difundida.

\subsubsection{Porcentaje del total dentro de cada grupo}

Una pregunta clásica: ``¿qué porcentaje representa cada cosa \emph{dentro}
de su grupo?''. La receta es: primero resumes con \codigo{summarise()} y
después, con el resultado todavía agrupado por el nivel superior, calculas
el porcentaje con \codigo{mutate()}.

\begin{ejemplo}{Mezcla de métodos de pago por trimestre}
Finanzas negocia las comisiones bancarias y quiere saber qué porcentaje de
los ingresos de cada trimestre entró por cada método de pago.
\end{ejemplo}

\begin{rcode}
mezcla_pago <- transacciones %>%
  group_by(trimestre, metodo_pago) %>%
  summarise(ingresos = sum(total_transaccion),
            .groups = "drop_last") %>%   # queda agrupado por trimestre
  mutate(pct_trimestre = round(ingresos / sum(ingresos) * 100, 1)) %>%
  ungroup()                               # quitamos el último grupo
mezcla_pago %>% filter(trimestre %in% c("Q1", "Q4"))
\end{rcode}

3 Q1        Tarjeta Débito    51032.          21.3

\subsubsection{Agrupar sin resumir: \texorpdfstring{\codigo{group\_by()}}{group\_by()} + \texorpdfstring{\codigo{mutate()}}{mutate()}}

\codigo{group\_by()} también funciona con \codigo{mutate()}: en lugar de
reducir cada grupo a una fila, conserva todas las filas y calcula dentro de
cada grupo. Es perfecto para comparar cada registro contra el promedio de su
grupo.

\begin{ejemplo}{¿Qué ventas están muy por encima del promedio de su tienda?}
Para detectar ventas atípicas no basta con compararlas contra el promedio
general: una venta de \$3,000 puede ser normal en una tienda y excepcional
en otra.
\end{ejemplo}

\begin{rcode}
ventas_vs_tienda <- ventas %>%
  group_by(tienda_id) %>%
  mutate(
    promedio_tienda = mean(total),              # promedio de SU tienda
    veces_promedio  = round(total / promedio_tienda, 2)
  ) %>%
  ungroup()                                     # ¡no lo olvides!

ventas_vs_tienda %>%
  select(fecha, tienda_id, total, promedio_tienda, veces_promedio) %>%
  slice_max(veces_promedio, n = 4)
\end{rcode}
\begin{rsalida}

La venta del 21 de abril en la tienda 2 fue 3.41 veces el promedio de

\begin{advertencia}
Una tabla agrupada \emph{recuerda} sus grupos. Si olvidas
\codigo{ungroup()}, los pasos siguientes (un \codigo{mutate()}, un

sin que te des cuenta. Cuando imprimas una tabla y veas una línea
\texttt{\# Groups: tienda\_id [10]} debajo del encabezado, esa tabla sigue
agrupada.
\end{advertencia}

\subsubsection{Valores faltantes en los resúmenes}

Si una columna tiene aunque sea un \codigo{NA}, su suma y su promedio serán

metas %>%

\end{rcode}

\section{Funciones de ventana para KPIs}
\label{sec:m2-ventana}

Las funciones de resumen (\codigo{sum()}, \codigo{mean()}\ldots) convierten
muchos valores en uno. Las \termino{funciones de ventana} (\emph{window
functions}) devuelven \emph{un valor por cada fila}, pero calculado mirando
a otras filas: la anterior, la siguiente, todas las previas o todo el grupo.
Con ellas se calculan casi todos los KPIs de tendencia de un tablero de BI.

ventas_mensuales <- ventas %>%

\subsection{Crecimiento mes contra mes (MoM) y acumulado del año (YTD)}

El \termino{crecimiento mes contra mes} (MoM, \emph{month over month}) mide
cuánto cambió un indicador respecto al mes anterior:
\[
\text{MoM} = \left(\frac{\text{ingresos del mes}}{\text{ingresos del mes
anterior}} - 1\right) \times 100 .
\]
El \termino{acumulado del año} (YTD, \emph{year to date}) es la suma de
todos los meses del año hasta el mes actual.

\begin{rcode}
kpis_mensuales <- ventas_mensuales %>%
  mutate(
    mes_anterior = lag(ingresos),                    # fila previa
    mom_pct      = (ingresos / lag(ingresos) - 1) * 100,
    ytd          = cumsum(ingresos)                  # acumulado
  )

kpis_mensuales %>%
  mutate(across(where(is.numeric), ~ round(.x, 1))) %>%
  select(mes, ingresos, mes_anterior, mom_pct, ytd)
\end{rcode}

antes, y en la sección~\ref{sec:m2-complete} verás cómo rellenar los meses

\subsection{Participación y promedio móvil}

La \termino{participación} de cada mes es su porcentaje del total anual. El
\termino{promedio móvil} de 3 meses suaviza los altibajos: en cada mes
promedia ese mes y los dos anteriores, y deja ver la tendencia de fondo.
\codigo{lag(x, 2)} es el valor de dos filas atrás.

  )

kpis_mensuales %>%
  mutate(across(where(is.numeric), ~ round(.x, 1))) %>%
  select(mes, ingresos, participacion, prom_movil_3m, vs_siguiente)
\end{rcode}

\begin{ejemplo}{Análisis ABC (Pareto) de productos}
El principio de Pareto dice que pocos productos generan la mayor parte de las
ventas. El \termino{análisis ABC} clasifica los productos en: \textbf{A}, los
que acumulan el primer 80\% de los ingresos; \textbf{B}, el siguiente 15\%;
y \textbf{C}, el último 5\%. ¿Cuántos productos hay en cada clase?
\end{ejemplo}

\begin{rcode}
abc_productos <- ventas %>%
  group_by(producto_id) %>%
  summarise(ingresos = sum(total), .groups = "drop") %>%
  arrange(desc(ingresos)) %>%                    # del mejor al peor
  mutate(
    pct_acumulado = cumsum(ingresos) / sum(ingresos) * 100,
    clase = case_when(
      pct_acumulado <= 80 ~ "A",
      pct_acumulado <= 95 ~ "B",
      .default            = "C"
    )
  )

abc_productos %>%
  group_by(clase) %>%
  summarise(productos = n(), ingresos = sum(ingresos),
            .groups = "drop") %>%
  mutate(pct_ingresos = round(ingresos / sum(ingresos) * 100, 1))
\end{rcode}
\begin{rsalida}
# A tibble: 3 x 4
  clase productos ingresos pct_ingresos
  <chr>     <int>    <dbl>        <dbl>
1 A            31  402751.         78.4
2 B            12   83751.         16.3
3 C             7   27415.          5.3
\end{rsalida}

Aquí \codigo{cumsum()} se aplica después de ordenar de mayor a menor, así que
\codigo{pct\_acumulado} dice qué porcentaje de los ingresos suman los
mejores productos hasta esa fila. El resultado es interesante porque
\emph{no} sigue el 80/20 clásico: se necesitan 31 de los 50 productos (62\%)
para juntar el 78.4\% de los ingresos. Las ventas de esta empresa están
poco concentradas, así que descontinuar productos de clase C (7 productos,
5.3\% de los ingresos) tendría poco impacto en la venta. En una empresa real
este análisis guía decisiones de inventario: a los productos A nunca les
debe faltar existencia.

\section{Fechas con \texorpdfstring{\paquete{lubridate}}{lubridate}}
\label{sec:m2-fechas}

Casi todo análisis de BI tiene una dimensión de tiempo: ventas por mes,
comparaciones contra el año anterior, antigüedad de clientes, días sin
comprar. \paquete{lubridate} (incluido en el \emph{tidyverse} desde la
versión 2.0) hace que trabajar con fechas sea sencillo.

\subsection{Convertir texto en fechas}

Las fechas llegan como texto en mil formatos: \texttt{2023-03-15},
\texttt{15/03/2023}, \texttt{03/15/2023} (formato de Estados Unidos)\ldots{}
\paquete{lubridate} tiene una función por cada \emph{orden} de los
componentes: \codigo{ymd()} (año-mes-día), \codigo{dmy()} (día-mes-año) y
\codigo{mdy()} (mes-día-año). Los separadores no importan.

\begin{rcode}
ymd("2023-03-15")            # año, mes, día
dmy("15/03/2023")            # día, mes, año (formato de México)
mdy("03-15-2023")            # mes, día, año (formato de EE. UU.)
dmy("15 de marzo de 2023")   # ¡entiende meses en español!
ymd(20230315)                # también números tipo AAAAMMDD
\end{rcode}
\begin{rsalida}
[1] "2023-03-15"
[1] "2023-03-15"
[1] "2023-03-15"
[1] "2023-03-15"
[1] "2023-03-15"
\end{rsalida}

Las cinco dan la misma fecha. El resultado es un objeto de clase
\codigo{Date}: R ya sabe que es una fecha y puede ordenarla, restarla o
extraer sus partes. El texto \texttt{"15/03/2023"}, en cambio, es solo una
cadena de caracteres.

\begin{advertencia}
¿\texttt{03/04/2023} es 3 de abril o 4 de marzo? Depende de quién lo
escribió. Antes de convertir, pregunta de qué sistema viene el archivo y
revisa un valor con día mayor a 12 (como \texttt{15/03}) para confirmar el
orden. Si una fecha no se puede interpretar, \paquete{lubridate} devuelve
\codigo{NA} con la advertencia \texttt{failed to parse}.
\end{advertencia}

\subsection{Extraer componentes de una fecha}

\begin{ejemplo}{Enriquecer las ventas con atributos de calendario}
Para analizar estacionalidad necesitamos, por cada venta, el año, el número

\subsection{Diferencias entre fechas: antigüedad y recencia}

Restar dos fechas da un número de días (un objeto \codigo{difftime}). Hay
dos formas recomendadas de convertirlo en un número utilizable:

\begin{itemize}
  \item \codigo{as.numeric(difftime(fin, inicio, units = "days"))}: días
        (o semanas, horas\ldots) como número.
  \item \codigo{time\_length(interval(inicio, fin), "years")}: años (o
        meses) exactos, considerando años bisiestos y meses de distinta
        longitud.
\end{itemize}

Para que tus resultados sean reproducibles, usa siempre una \termino{fecha
de corte} fija en lugar de \codigo{Sys.Date()} (la fecha de hoy, que cambia
cada día). Nosotros usaremos el 1 de enero de 2024, justo después del cierre
del año de datos.

\begin{ejemplo}{Antigüedad de los clientes}
¿Cuántos años llevan registrados nuestros clientes? ¿Cuántos son clientes
nuevos (menos de un año)?

  )
clientes_antig %>%

  head(3)
clientes_antig %>% count(tipo_cliente)

\section{Texto con \texorpdfstring{\paquete{stringr}}{stringr}}
\label{sec:m2-stringr}

Nombres de clientes, ciudades, categorías, códigos de producto, correos:
buena parte de los datos de negocio es texto, y el texto casi siempre viene
``sucio''. Todas las funciones de \paquete{stringr} empiezan con
\codigo{str\_} (escribe \codigo{str\_} en RStudio y pulsa \tecla{Tab} para

\subsection{Mayúsculas, minúsculas y espacios}

\begin{rcode}
ciudades <- c("  cdmx", "Guadalajara ", "MONTERREY", "san  luis   potosí")

str_to_upper(ciudades)    # TODO EN MAYÚSCULAS
str_to_lower(ciudades)    # todo en minúsculas
str_to_title(ciudades)    # Tipo Título
str_trim(ciudades)        # quita espacios al inicio y al final
str_squish(ciudades)      # además, reduce espacios internos repetidos
\end{rcode}

[4] "SAN  LUIS   POTOSÍ"
[1] "  cdmx"             "guadalajara "       "monterrey"         
[4] "san  luis   potosí"
[1] "  Cdmx"             "Guadalajara "       "Monterrey"

\subsection{Buscar, reemplazar y extraer}

\begin{itemize}
  \item \codigo{str\_detect(x, patrón)}: ¿contiene el patrón?
        (\codigo{TRUE}/\codigo{FALSE}).
  \item \codigo{str\_replace\_all(x, patrón, reemplazo)}: reemplaza todas las
        apariciones (\codigo{str\_replace()} solo la primera).
  \item \codigo{str\_sub(x, inicio, fin)}: extrae por posición.
  \item \codigo{str\_length(x)}: número de caracteres.
\end{itemize}

\begin{ejemplo}{Una campaña para la familia García}
Mercadotecnia prepara una campaña de apellidos y quiere a los clientes cuyo
nombre contiene ``García''. Además, para el CRM necesita el teléfono sin

\end{ejemplo}

\begin{rcode}

    tel_limpio = str_replace_all(telefono, "-", ""), # quita guiones
    lada       = str_sub(telefono, 1, 2)             # caracteres 1 a 2
  ) %>%
  select(cliente_id, nombre, telefono, tel_limpio, lada) %>%
  head(4)
\end{rcode}

\begin{consejo}
Los patrones de \paquete{stringr} son \termino{expresiones regulares}
(\emph{regex}), un minilenguaje para describir texto. No necesitas dominarlas
para empezar; estos cuatro símbolos resuelven la mayoría de los casos:
\codigo{\textasciicircum{}} (inicio del texto: \codigo{"\textasciicircum{}Tarjeta"}),
\codigo{\$} (final: \codigo{"com\$"}), \codigo{|} (o:
\codigo{"CDMX|Toluca"}) y \codigo{[0-9]} (cualquier dígito). Si buscas un
carácter especial como punto o signo de pesos de forma literal, usa
\codigo{fixed(".")}.
\end{consejo}

\subsection{Rellenar y armar códigos: \texorpdfstring{\codigo{str\_pad()}}{str\_pad()} y \texorpdfstring{\codigo{str\_c()}}{str\_c()}}

\section{Unir tablas: los \emph{joins}}
\label{sec:m2-joins}

La tabla \codigo{ventas} dice que el 1 de enero se vendió el producto 31 al
cliente 94 en la tienda 6. Pero ¿qué producto es el 31? ¿De qué categoría?
¿En qué ciudad está la tienda 6? Esa información vive en otras tablas. Un
\termino{join} (unión) combina dos tablas usando una o más columnas en común,
llamadas \termino{llaves} (\emph{keys}). Es el equivalente de
\codigo{BUSCARV}/\codigo{XLOOKUP} de Excel, pero para todas las columnas y
todas las filas a la vez, y es la operación más importante de BI.

\subsection{Tipos de \emph{join}}

Todos los \emph{joins} de \paquete{dplyr} tienen la forma
\codigo{tipo\_join(x, y, by = "llave")}, donde \codigo{x} es la tabla
``izquierda'' (normalmente la de hechos) y \codigo{y} la ``derecha''
(normalmente la dimensión). La figura~\ref{fig:m2-joins} resume qué filas
conserva cada uno.

Para verlos en acción usemos dos tablas diminutas donde es fácil seguir cada

                        nombre = c("Café", "Té", "Azúcar"))

left_join(ventas_mini, catalogo_mini, by = "producto_id")
inner_join(ventas_mini, catalogo_mini, by = "producto_id")
full_join(ventas_mini, catalogo_mini, by = "producto_id")
\end{rcode}

\begin{itemize}
  \item \codigo{left\_join()} conserva las 3 ventas; la del producto 99 queda
        con \codigo{NA} en \codigo{nombre}. Es el \emph{join} que usarás el
        90\% de las veces, porque nunca pierde filas de tu tabla de hechos.
  \item \codigo{inner\_join()} solo conserva las 2 ventas con producto
        conocido. Cuidado: la venta 3 \emph{desaparece en silencio} y tus
        totales bajan.
  \item \codigo{full\_join()} conserva todo: las 3 ventas y el producto 30
        sin ventas (con \codigo{NA} en \codigo{venta} y \codigo{unidades}).
  \item \codigo{right\_join(x, y)} es un \codigo{left\_join(y, x)} con las
        columnas en otro orden; casi no se usa.
\end{itemize}

Los \emph{filtering joins} no agregan columnas: solo deciden qué filas de
\codigo{x} se quedan.

\begin{rcode}
semi_join(ventas_mini, catalogo_mini, by = "producto_id") # con pareja
anti_join(ventas_mini, catalogo_mini, by = "producto_id") # sin pareja
anti_join(catalogo_mini, ventas_mini, by = "producto_id") # sin ventas
\end{rcode}

# A tibble: 1 x 2
  producto_id nombre
        <dbl> <chr> 
1          30 Azúcar
\end{rsalida}

El último \codigo{anti\_join()} invierte las tablas y responde otra
pregunta: ¿qué productos del catálogo no se vendieron? El orden de las
tablas importa.

\subsubsection{Llaves con nombres distintos: \texorpdfstring{\codigo{by = c(...)}}{by = c(...)} y \texorpdfstring{\codigo{join\_by()}}{join\_by()}}

{\sloppy En \codigo{ventas} el vendedor se identifica con \codigo{vendedor\_id}, pero
en \codigo{empleados} la llave se llama \codigo{empleado\_id}. Hay dos formas
de indicarlo:\par}

\begin{rcode}
# Forma clásica: c("nombre en x" = "nombre en y")
v1 <- ventas %>%
  left_join(empleados, by = c("vendedor_id" = "empleado_id"))

# Forma moderna (dplyr 1.1+): join_by() con ==
v2 <- ventas %>%
  left_join(empleados, join_by(vendedor_id == empleado_id))

identical(v1, v2)       # ¿dan exactamente lo mismo?
\end{rcode}

[1] TRUE
\end{rsalida}

desigualdad (por ejemplo, \codigo{join\_by(producto\_id, fecha >= inicio)}
para buscar el precio vigente en cada fecha), que son muy útiles pero
rebasan este módulo.\par}

\subsubsection{Columnas con el mismo nombre: \texorpdfstring{\codigo{suffix}}{suffix}}

Si las dos tablas tienen una columna con el mismo nombre que \emph{no} es la
llave, \paquete{dplyr} conserva ambas y les agrega los sufijos \codigo{.x} y
\codigo{.y}. Pasa con \codigo{ciudad}, que existe en \codigo{clientes} y en
\codigo{tiendas}. Con \codigo{suffix} eliges sufijos que se entiendan.

\begin{ejemplo}{¿Nuestros clientes compran en su ciudad?}
¿Qué porcentaje de las ventas se hace en una tienda de la misma ciudad donde
vive el cliente?
\end{ejemplo}

  left_join(clientes, by = "cliente_id") %>%
  left_join(tiendas, by = "tienda_id",
            suffix = c("_cliente", "_tienda"))   # en vez de .x / .y

ventas_ciudad %>%
  select(fecha, ciudad_cliente, ciudad_tienda) %>%
  head(3)

ventas_ciudad %>%
  summarise(pct_misma_ciudad =
              mean(ciudad_cliente == ciudad_tienda) * 100)
\end{rcode}

\subsection{La trampa de las llaves duplicadas}

Un \codigo{left\_join()} conserva todas las filas de \codigo{x}\ldots{} y
puede \emph{agregar} filas. Si una llave aparece dos veces en \codigo{y},
cada fila de \codigo{x} con esa llave se duplica. A esto se le llama la
\termino{explosión de filas}, y es la causa número uno de totales inflados
en los reportes.

\begin{ejemplo}{La tabla de precios con historial}
Compras te pasa una tabla de precios, sin avisarte que el producto 31 tiene
dos registros: el precio anterior y el vigente. La unes con las ventas del
1 de enero.
\end{ejemplo}

\begin{rcode}
precios_compras <- tibble(
  producto_id = c(31, 31, 15),
  vigencia    = c("2022", "2023", "2023"),
  precio_lista = c(340, 355, 290)
)
ventas_ene <- ventas %>%
  filter(fecha <= as.Date("2023-01-02")) %>%
  select(fecha, producto_id, total)
ventas_ene
ventas_ene %>% left_join(precios_compras, by = "producto_id")
\end{rcode}
\begin{rsalida}
# A tibble: 2 x 3
  fecha      producto_id total
  <date>           <dbl> <dbl>
1 2023-01-01          31 3333.
2 2023-01-02          15 2262 
# A tibble: 3 x 5
  fecha      producto_id total vigencia precio_lista
  <date>           <dbl> <dbl> <chr>           <dbl>
1 2023-01-01          31 3333. 2022              340
2 2023-01-01          31 3333. 2023              355
3 2023-01-02          15 2262  2023              290
\end{rsalida}

¡Dos ventas se convirtieron en tres! Si ahora sumaras \codigo{total}, el
1 de enero contaría doble. \paquete{dplyr} no se queja porque, en esta
dirección, cada fila de \codigo{precios\_compras} encaja con una sola venta.
Tres defensas:

\begin{enumerate}
  \item \textbf{Revisa la llave antes de unir.} En una dimensión, cada llave
        debe aparecer una sola vez:
\end{enumerate}

\begin{rcode}
precios_compras %>%
  count(producto_id) %>%
  filter(n > 1)             # llaves repetidas: debería salir vacío
\end{rcode}
\begin{rsalida}
# A tibble: 1 x 2
  producto_id     n
        <dbl> <int>
1          31     2
\end{rsalida}

\begin{enumerate}[resume]
  \item \textbf{Declara la relación que esperas.} Con
        \codigo{relationship = "many-to-one"} (muchas ventas por cada
        producto, un producto por llave) \paquete{dplyr} se detiene con un
        error si la tabla derecha tiene llaves repetidas, en lugar de
        duplicar filas en silencio:
\end{enumerate}

\begin{rnoejecutar}
ventas_ene %>%
  left_join(precios_compras, by = "producto_id",
            relationship = "many-to-one")
\end{rnoejecutar}
\begin{rsalida}
Error in `left_join()`:
! Each row in `x` must match at most 1 row in `y`.
i Row 1 of `x` matches multiple rows in `y`.
\end{rsalida}

\begin{enumerate}[resume]
  \item \textbf{Compara filas antes y después} del \emph{join}, como vimos
        en el consejo anterior.
\end{enumerate}

Cuando las llaves se repiten en \emph{ambas} tablas (relación
``muchos a muchos''), \paquete{dplyr} sí te avisa con una advertencia
(\texttt{Detected an unexpected many-to-many relationship}). No la ignores:
casi siempre significa que te falta una columna en la llave (por ejemplo,
unir por producto \emph{y} por fecha de vigencia).

\subsection{\texorpdfstring{\codigo{anti\_join()}}{anti\_join()} para auditar la calidad de los datos}

Los \emph{filtering joins} son la herramienta favorita del auditor de datos.
Preguntas como ``¿hay ventas de productos que no existen?'' o ``¿qué
clientes nunca compraron?'' se responden con una línea.

\begin{rcode}
# 1. ¿Ventas con un producto que no está en el catálogo? (huérfanas)
ventas %>% anti_join(productos, by = "producto_id") %>% nrow()

# 2. ¿Productos del catálogo que no se vendieron en ventas?
productos %>% anti_join(ventas, by = "producto_id") %>% nrow()

# 3. ¿Clientes registrados que no compraron en 2023?
clientes_sin_compra <- clientes %>%
  anti_join(ventas, by = "cliente_id")
nrow(clientes_sin_compra)

# 4. De los que sí compraron (semi_join), ¿cuántos son premium?
clientes %>%
  semi_join(ventas, by = "cliente_id") %>%
  count(es_premium)
\end{rcode}
\begin{rsalida}

[1] 0
[1] 28

1 FALSE        107

mercadotecnia. De los 172 que sí compraron, 65 (38\%) son premium.

Las tres primeras filas son los casos más ``cercanos'': compras hechas
entre 4 y 14 días antes del registro. En total, 42 ventas (11.5\%) son de
clientes que, según el sistema, todavía no existían. En una empresa real las explicaciones típicas son: el cliente
compró como invitado y se registró después, o la fecha de registro se
sobrescribió al actualizar sus datos. Sea cual sea la causa, es un hallazgo
que conviene documentar. Observa el truco de unir solo las columnas que
necesitas con \codigo{select()} dentro del \emph{join}: la tabla resultante
queda más limpia.

\subsection{Apilar tablas: \texorpdfstring{\codigo{bind\_rows()}}{bind\_rows()} y \texorpdfstring{\codigo{bind\_cols()}}{bind\_cols()}}

A veces no necesitas unir por una llave, sino \emph{apilar}: cada mes el
sistema te manda un archivo con las ventas de ese mes y quieres un solo
archivo del año. \codigo{bind\_rows()} pone tablas una debajo de otra,
emparejando las columnas por nombre.

\begin{rcode}
# Simulamos tres archivos mensuales
enero   <- ventas %>% filter(mes == "2023-01")
febrero <- ventas %>% filter(mes == "2023-02")
marzo   <- ventas %>% filter(mes == "2023-03") %>%
  select(-dia_semana)               # a marzo le falta una columna

primer_trimestre <- bind_rows(enero, febrero, marzo,
                              .id = "archivo")   # de qué tabla vino
primer_trimestre %>% count(archivo)
primer_trimestre %>% filter(is.na(dia_semana)) %>% nrow()
\end{rcode}
\begin{rsalida}
# A tibble: 3 x 2
  archivo     n
  <chr>   <int>
1 1          31
2 2          28
3 3          31
[1] 31
\end{rsalida}

El argumento \codigo{.id} agrega una columna con el número de tabla de
origen (con una lista con nombres, \codigo{list(ene = enero, \ldots)},
pondría el nombre). Como a marzo le faltaba \codigo{dia\_semana},
\codigo{bind\_rows()} no falla: llena esa columna con \codigo{NA} en sus 31
filas. Si en lugar de faltar una columna tuviera otro \emph{tipo} (texto en
un archivo y número en otro), sí fallaría; lo verás en la
sección~\ref{sec:m2-errores}.

\codigo{bind\_cols()} pega tablas lado a lado \emph{por posición}. Úsala
con mucho cuidado: no verifica que la fila 1 de una tabla corresponda a la
fila 1 de la otra. Si existe una llave, usa un \emph{join}.

\begin{consejo}
Para leer y apilar de una vez todos los CSV de una carpeta, \paquete{readr}
acepta un vector de rutas:
\codigo{read\_csv(list.files("datos/mensuales", full.names = TRUE), id =
"archivo")}. El argumento \codigo{id} guarda la ruta de origen de cada fila.
\end{consejo}

\section{Cambiar la forma de las tablas con \texorpdfstring{\paquete{tidyr}}{tidyr}}

\begin{itemize}

\subsection{\texorpdfstring{\codigo{pivot\_longer()}}{pivot\_longer()}: ordenar un reporte de Excel}

\begin{ejemplo}{El presupuesto que llegó en Excel}

    cols      = Ene:Jun,          # columnas a "derretir"

presupuesto_largo

\end{ejemplo}

                  "CDMX", "Puebla", "Mérida"),
  ventas      = c(54066, 70155, 54846, 43899, 53611, NA),

\subsection{Rellenar periodos sin ventas: \texorpdfstring{\codigo{complete()}}{complete()}}
\label{sec:m2-complete}

Recuerda la advertencia sobre \codigo{lag()}: si falta un mes, el
crecimiento ``mes contra mes'' se calcula contra el mes equivocado. Y los
meses sin ventas no aparecen en un resumen, simplemente porque no hay filas.

\begin{ejemplo}{¿Hubo tiendas con meses en cero?}
Con 10 tiendas y 12 meses deberíamos tener 120 combinaciones de tienda y
mes. ¿Las tenemos?
\end{ejemplo}

\begin{rcode}
ventas_tienda_mes <- ventas %>%
  group_by(tienda_id, mes) %>%
  summarise(ingresos = sum(total), .groups = "drop")
nrow(ventas_tienda_mes)            # ¿120?

ventas_tienda_mes_completa <- ventas_tienda_mes %>%
  complete(tienda_id, mes,                 # todas las combinaciones
           fill = list(ingresos = 0))      # con 0 donde no hubo ventas
nrow(ventas_tienda_mes_completa)

ventas_tienda_mes_completa %>% filter(ingresos == 0)
\end{rcode}
\begin{rsalida}
[1] 118
[1] 120
# A tibble: 2 x 3
  tienda_id mes     ingresos
      <dbl> <chr>      <dbl>
1         1 2023-08        0
2         4 2023-06        0
\end{rsalida}

Solo había 118 combinaciones: la tienda 1 no vendió nada en agosto y la
tienda 4 nada en junio. \codigo{complete()} crea las filas faltantes con
todas las combinaciones de los valores existentes de \codigo{tienda\_id} y
\codigo{mes}, y \codigo{fill} les pone 0. Ahora sí, un \codigo{lag()} por
tienda compararía cada mes contra el anterior real. (Si un mes no aparece en
\emph{ninguna} tienda, \codigo{complete()} no puede inventarlo; en ese caso
se le da la lista completa, por ejemplo \codigo{complete(mes =
meses\_del\_anio)}.)

\codigo{distinct()} sin argumentos elimina las filas que son idénticas en
\emph{todas} las columnas. Si dos filas tuvieran el mismo folio pero algún
dato distinto, no las quitaría: ese caso requiere investigar cuál es la
correcta. (\codigo{distinct(folio, .keep\_all = TRUE)} conservaría la
primera aparición de cada folio.)

\section{Caso práctico integral: reporte mensual de ventas 2023}
\label{sec:m2-caso}

Regresemos al mensaje de la directora comercial del inicio del módulo. Vas a
construir, con todo lo aprendido, un reporte completo que se exporta a un
archivo de Excel con varias hojas. El código de esta sección está pensado
para que lo copies en un script propio (por ejemplo
\archivo{reporte\_mensual.R}) y lo vuelvas a ejecutar cada mes.

\begin{negocio}{Qué se pide}
\begin{enumerate}
  \item KPIs globales del año: ingresos, ventas, unidades, ticket promedio,
        clientes únicos, descuento promedio y utilidad bruta.
  \item Ventas por mes con crecimiento contra el mes anterior y acumulado.
  \item Ventas por categoría con participación y ranking.
  \item Los cinco mejores clientes.
  \item El ranking de tiendas y el desempeño de los vendedores.
  \item Una tabla dinámica de mes $\times$ categoría.
  \item Un apartado de calidad de datos con lo que haya que aclarar.
\end{enumerate}
\end{negocio}

\subsection{Paso 1: la tabla maestra}

En BI se acostumbra construir una \termino{tabla maestra} (o tabla
``plana''): los hechos unidos con todas las dimensiones que se van a usar.
Unimos solo las columnas necesarias y les damos nombres claros para evitar
choques (\codigo{nombre} existe en clientes y en empleados; \codigo{ciudad},
en clientes y en tiendas).

\begin{rcode}[title=Reporte mensual: tabla maestra]
maestra <- ventas %>%
  left_join(select(productos, producto_id, nombre_producto, categoria,
                   precio_catalogo, costo),
            by = "producto_id") %>%
  left_join(select(clientes, cliente_id, cliente = nombre,
                   ciudad_cliente = ciudad, es_premium),
            by = "cliente_id") %>%
  left_join(select(tiendas, tienda_id, nombre_tienda,
                   ciudad_tienda = ciudad, zona),
            by = "tienda_id") %>%
  left_join(select(empleados, empleado_id, vendedor = nombre),
            join_by(vendedor_id == empleado_id)) %>%
  mutate(
    mes_fecha   = floor_date(fecha, "month"),
    mes_nombre  = month(fecha, label = TRUE),
    costo_total = costo * cantidad,          # costo de lo vendido
    utilidad    = total - costo_total        # utilidad bruta
  )

# Control: los joins no deben agregar ni quitar filas
stopifnot(nrow(maestra) == nrow(ventas))
dim(maestra)
\end{rcode}
\begin{rsalida}
[1] 365  29
\end{rsalida}

\codigo{stopifnot()} detiene el script con un error si la condición es
falsa. Es un \termino{control automático}: si algún mes el catálogo trae una
llave duplicada, el reporte no se generará con totales inflados, sino que
se detendrá y te avisará. Dentro de \codigo{select()} renombramos al vuelo
(\codigo{cliente = nombre}).

Como ejemplo, esta consulta SQL y el \emph{pipeline} de \paquete{dplyr}
debajo de ella producen el mismo resultado:

\begin{sqlcode}
SELECT p.categoria,
       SUM(v.total)  AS ingresos,
       COUNT(*)      AS ventas
FROM ventas v
LEFT JOIN productos p ON v.producto_id = p.producto_id
WHERE v.trimestre = 'Q4'
GROUP BY p.categoria
ORDER BY ingresos DESC
LIMIT 3;
\end{sqlcode}

\begin{rcode}
ventas %>%
  left_join(productos, by = "producto_id") %>%      # LEFT JOIN
  filter(trimestre == "Q4") %>%                     # WHERE
  group_by(categoria) %>%                           # GROUP BY
  summarise(ingresos = sum(total), ventas = n(),    # SUM, COUNT
            .groups = "drop") %>%
  arrange(desc(ingresos)) %>%                       # ORDER BY DESC
  head(3)                                           # LIMIT 3
\end{rcode}
\begin{rsalida}
# A tibble: 3 x 3
  categoria   ingresos ventas
  <chr>          <dbl>  <int>
1 Belleza       27050.     20
2 Electrónica   19900.     12
3 Juguetes      18363.      9
\end{rsalida}

Una diferencia importante: en SQL el orden de escritura (\texttt{SELECT}
primero) no es el orden en que se ejecuta. En \paquete{dplyr} escribes los
pasos en el orden en que suceden, y eso lo hace más fácil de leer y de
depurar: puedes ejecutar el \emph{pipeline} hasta cualquier línea y ver el
resultado intermedio.

\section{Errores comunes}
\label{sec:m2-errores}

Estos son los errores que más verás mientras aprendes. Los mensajes son los
que R muestra realmente (algunos en inglés porque vienen de los paquetes,
otros en español porque vienen de R base).

\subsection{Olvidar un pipe o ponerlo al inicio de la línea}

\begin{rnoejecutar}
ventas %>%
  filter(total > 4800)      # <- falta %>% al final de esta línea
  arrange(desc(total))
\end{rnoejecutar}
\begin{rsalida}
Error: objeto 'total' no encontrado
\end{rsalida}

R ejecuta las dos primeras líneas como una instrucción completa (y muestra
el resultado del filtro) y luego intenta ejecutar
\codigo{arrange(desc(total))} sola, sin tabla: no sabe qué es
\codigo{total}. Si pones el pipe al inicio de la línea siguiente, el error
es otro, porque la primera línea ya era una instrucción completa:

\begin{rnoejecutar}
ventas
  %>% filter(total > 4800)
\end{rnoejecutar}
\begin{rsalida}
Error: inesperado SPECIAL en "  %>%"
\end{rsalida}

\textbf{Solución}: el \codigo{\%>\%} siempre va al \emph{final} de la línea,
y la última línea del \emph{pipeline} no lleva pipe.

\subsection{Usar \texorpdfstring{\codigo{=}}{=} en lugar de \texorpdfstring{\codigo{==}}{==} en \texorpdfstring{\codigo{filter()}}{filter()}}

\begin{rnoejecutar}
ventas %>% filter(tienda_id = 3)
\end{rnoejecutar}
\begin{rsalida}
Error in `filter()`:
! We detected a named input.
i This usually means that you've used `=` instead of `==`.
i Did you mean `tienda_id == 3`?
\end{rsalida}

\codigo{=} asigna o nombra argumentos; \codigo{==} compara. El mensaje de
\paquete{dplyr} incluso te sugiere la corrección.

\subsection{Olvidar cargar \texorpdfstring{\paquete{dplyr}}{dplyr}: el \texorpdfstring{\codigo{filter()}}{filter()} equivocado}

Si abres una sesión nueva y olvidas \codigo{library(tidyverse)},
\codigo{filter()} existe de todos modos: es \codigo{stats::filter()}, una
función para series de tiempo que no entiende nombres de columna.

\begin{rnoejecutar}
# Sesión nueva, sin library(tidyverse)
ventas <- readr::read_csv("datasets/ventas_retail.csv",
                          show_col_types = FALSE)
filter(ventas, total > 4800)
\end{rnoejecutar}
\begin{rsalida}
Error: objeto 'total' no encontrado
\end{rsalida}

El mismo error puede aparecer si otro paquete cargado \emph{después} del
\emph{tidyverse} tapa a \codigo{filter()} o \codigo{select()} (pasa, por
ejemplo, con \paquete{MASS}, que tiene su propio \codigo{select()}).
\textbf{Solución}: carga los paquetes al inicio del script y, ante la duda,
escribe \codigo{dplyr::filter()} o \codigo{dplyr::select()}.

\subsection{Escribir mal el nombre de una columna}

\begin{rnoejecutar}
ventas %>% summarise(total = sum(Total))    # "Total" con mayúscula
\end{rnoejecutar}
\begin{rsalida}
Error in `summarise()`:
i In argument: `total = sum(Total)`.
Caused by error:
! objeto 'Total' no encontrado
\end{rsalida}

{\sloppy R distingue mayúsculas de minúsculas. Revisa los nombres exactos con
\codigo{names(ventas)} o \codigo{glimpse(ventas)}.\par}

\subsection{Nombres de columna con espacios}

Los archivos de Excel suelen traer encabezados como ``Ventas Totales''. Ese
nombre tiene un espacio, así que no puedes escribirlo tal cual:

\begin{rnoejecutar}
reporte %>% select(Ventas Totales)
\end{rnoejecutar}
\begin{rsalida}
Error: unexpected symbol en "reporte %>% select(Ventas Totales"
\end{rsalida}

\textbf{Solución}: escríbelo entre comillas invertidas (\emph{backticks}),
o mejor aún, renómbralo en cuanto lo leas:

\begin{rcode}
reporte <- tibble(`Ventas Totales` = c(100, 200),
                  `Sucursal ID` = c("A", "B"))
reporte %>%
  rename(ventas_totales = `Ventas Totales`,     # backticks
         sucursal_id    = `Sucursal ID`)
\end{rcode}
\begin{rsalida}
# A tibble: 2 x 2
  ventas_totales sucursal_id
           <dbl> <chr>      
1            100 A          
2            200 B          
\end{rsalida}

(El paquete \paquete{janitor} tiene la función \codigo{clean\_names()}, que
convierte todos los nombres a \texttt{snake\_case} de una vez.)

\subsection{\texorpdfstring{\codigo{group\_by()}}{group\_by()} sin \texorpdfstring{\codigo{summarise()}}{summarise()} (o sin \texorpdfstring{\codigo{ungroup()}}{ungroup()})}

\codigo{group\_by()} solo, no resume nada: la tabla se ve igual, con una
línea extra de \texttt{Groups}. Si esperabas un total por grupo, te faltó
el \codigo{summarise()}. Y si la tabla queda agrupada, los pasos siguientes
se hacen por grupo:

\begin{rcode}
agrupada <- ventas %>% group_by(tienda_id)
agrupada %>% select(fecha, tienda_id, total) %>% head(2)

# Con grupos: slice_max() da la mejor venta DE CADA tienda (10 filas)
agrupada %>% slice_max(total, n = 1) %>% nrow()
# Sin grupos: la mejor venta del año (1 fila)
agrupada %>% ungroup() %>% slice_max(total, n = 1) %>% nrow()
\end{rcode}
\begin{rsalida}
# A tibble: 2 x 3
# Groups:   tienda_id [2]
  fecha      tienda_id total
  <date>         <dbl> <dbl>
1 2023-01-01         6 3333.
2 2023-01-02         5 2262 
[1] 10
[1] 1
\end{rsalida}

Observa la línea \texttt{\# Groups: tienda\_id [2]}: la tabla sigue
agrupada (en las 2 filas mostradas hay 2 tiendas distintas). El mismo
\codigo{slice\_max(total, n = 1)} devuelve 10 filas o 1 fila según haya
grupos o no: si no te das cuenta de que la tabla está agrupada, tu ``venta
récord'' serán diez.

\subsection{Joins que multiplican filas}

\begin{rnoejecutar}
ventas_ene %>% left_join(precios_compras, by = "producto_id")
# ¿3 filas en lugar de 2? -> llave duplicada en la tabla derecha
\end{rnoejecutar}

No hay mensaje de error: ese es el peligro. Revisa siempre las filas antes y
después, y usa \codigo{count(llave) \%>\% filter(n > 1)} o
\codigo{relationship = "many-to-one"} (sección~\ref{sec:m2-joins}). Cuando la
duplicidad está en ambas tablas, verás:

\begin{rsalida}
Warning message:
...
  Detected an unexpected many-to-many relationship between `x` and `y`.
...
\end{rsalida}

\subsection{\texttt{NA} en sumas y promedios}

Una sola celda vacía convierte el total en \codigo{NA}
(sección~\ref{sec:m2-summarise}). Usa \codigo{na.rm = TRUE} a conciencia
y cuenta los faltantes con \codigo{sum(is.na(x))}.

\subsection{Apilar tablas con tipos distintos}

\begin{rnoejecutar}
a <- tibble(id = 1, monto = "100")    # monto como texto
b <- tibble(id = 2, monto = 200)      # monto como número
bind_rows(a, b)
\end{rnoejecutar}
\begin{rsalida}
Error in `bind_rows()`:
! Can't combine `..1$monto` <character> and `..2$monto` <double>.
\end{rsalida}

{\sloppy \textbf{Solución}: homologa los tipos antes de apilar, por ejemplo con
\codigo{mutate(monto = parse\_number(monto))} en la tabla de texto.\par}

\begin{resumen}
\begin{itemize}
  \item Los \textbf{datos ordenados} tienen una variable por columna, una
        observación por fila y un valor por celda. Analiza en largo,
        presenta en ancho.
  \item \codigo{read\_csv()} lee CSV y te informa los tipos que adivinó;
        \codigo{col\_types}, \codigo{na} y \codigo{problems()} te dan el
        control. \codigo{glimpse()} es tu primera mirada a cualquier tabla.
  \item El pipe (\codigo{\%>\%} o \codigo{|>}) se lee ``y luego'' y
        convierte tu análisis en una receta legible.
  \item Los verbos de \paquete{dplyr} (\codigo{filter}, \codigo{select},
        \codigo{mutate}, \codigo{arrange}, \codigo{summarise},
        \codigo{group\_by}) resuelven la mayoría de las preguntas de
        negocio. \codigo{count()} y \codigo{slice\_max()} son atajos
        valiosos.
  \item Las funciones de ventana (\codigo{lag()}, \codigo{cumsum()},
        \codigo{min\_rank()}) calculan crecimiento, acumulados y rankings.
  \item \paquete{lubridate} y \paquete{stringr} limpian y enriquecen fechas y
        texto. Usa una fecha de corte fija para resultados reproducibles.
  \item Los \emph{joins} conectan hechos con dimensiones; revisa siempre las
        filas antes y después, y usa \codigo{anti\_join()} para auditar.
  \item \paquete{tidyr} cambia la forma de las tablas y rellena faltantes y
        periodos vacíos.
  \item Un reporte profesional incluye controles automáticos, supuestos
        explícitos y hallazgos de calidad de datos.
\end{itemize}
\end{resumen}

script y límpiala: quita duplicados exactos, unifica la categoría (debe
quedar en tipo título y con acento), convierte el precio a número, convierte
la fecha (formatos mixtos), elimina los precios imposibles (cero o
negativos) y crea un SKU con formato \texttt{SKU-0001}. Al final, muestra el
precio promedio por categoría.
\begin{rnoejecutar}
lista_proveedor <- tibble(
  id        = c(1, 2, 2, 3, 4, 5, 6),
  categoria = c("electronica", "Electrónica ", "Electrónica ",
                "HOGAR", "hogar", "Ropa", " ropa"),
  precio    = c("$1,250.00", "$899.50", "$899.50", "450", "$0",
                "$320.75", "-15"),
  fecha     = c("2023-05-01", "02/05/2023", "02/05/2023", "2023-05-03",
                "04/05/2023", "2023-05-05", "06/05/2023")
)
\end{rnoejecutar}
